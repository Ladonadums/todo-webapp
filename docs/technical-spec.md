# TaskFlow — Техническое задание

## 1 Описание проекта

TaskFlow — это микросервисный API для управления личными задачами с поддержкой полнотекстового поиска, фоновой обработки и безопасной аутентификации.  
Пользователь может создавать, редактировать, фильтровать и искать задачи.  
Архитектура выбрана сервисная для масштабируемости, изоляции домена и гибкости развёртывания.

## 2 User Stories

- Как пользователь, я хочу зарегистрироваться через email и пароль.
- Как пользователь, я хочу войти и получить JWT-токен.
- Я могу создать задачу с заголовком, описанием, приоритетом и категорией.
- Я могу пометить задачу как выполненную.
- Я могу найти задачу по ключевому слову в заголовке или описании.
- Я могу фильтровать задачи по статусу (`is_done`) и минимальному приоритету.
- В будущем я получу уведомление о просроченных задачах.

## 3 Нефункциональные требования (НФТ)

- **SLA**: 99% uptime
- **RPS**: до 100 запросов/сек (MVP — низкая нагрузка).
- **Консистентность**: strong для задач, eventual для поиска
- **Безопасность**: пароли хешируются через `bcrypt`, токены — JWT с TTL 15 мин
- **Версионирование API**: `/api/v1/todos`
- **Формат ошибок**:
  ```json
  { "error": "InvalidInput", "message": "Title is too short" }
- **Пагинация**: `?page=1&size=20`

##  4. Сервисы (декомпозиция) — всё в одном репо
- **API Gateway**: Роутинг, аутентификация, rate limiting.Принимает все запросы, проверяет JWT, перенаправляет в Auth/Domain
- **Auth Service**: Регистрация, логин, выдача JWT. БД(PostgreSQL (`users`))
- **Domain Service (`Todo`)**: CRUD задачи, валидация, бизнес-логика. БД(PostgreSQL (`todos`).Принимает `todos` от Gateway
- **Search Service**: Полноценный поиск по задачам. БД(OpenSearch).Подписывается на события создания/обновления задач.
- **Worker Service**: Фоновые задачи (индексация, уведомления). БД(Redis (очередь)).Использует Celery + Redis.

##  5. Паттерны!
- **API Gateway** — централизованная точка входа для всех клиентов. Обеспечивает маршрутизацию запросов, проверку JWT-токенов и защиту от перегрузки (rate limiting). Упрощает клиентское взаимодействие и централизует безопасность.
- **Layered Architecture** — код каждого сервиса разделён на 3 слоя: presentation(FastAPI эндпоинты), service(бизнес-логика), repository(работа с БД).Это улучшает тестируемость, читаемость и поддерживаемость.
- **Repository Pattern** — Абстрагирует работу с PostgreSQL. Позволяет легко заменить СУБД или добавить моки в тестах без изменения бизнес-логики.
- **Service Layer** — бизнес-логикаВся бизнес-логика (валидация, преобразование данных, правила) вынесена в отдельный слой. Контроллеры (эндпоинты) не содержат логики — только вызов сервисов.
- **Event-Driven Architecture** — индексация в OpenSearch через события.При создании/обновлении задачи публикуется событие в Redis. Worker Service подписывается на эти события и индексирует данные в OpenSearch. Это развязывает сервисы и обеспечивает асинхронную обработку.
- **Dependency Injection** — для тестирования и гибкости.Зависимости (например, репозитории, внешние клиенты) передаются в сервисы через конструктор. Это упрощает unit-тестирование и позволяет легко подменять реализации.

##  6. Docker Compose

Система разворачивается через `docker-compose.yml` и включает следующие компоненты:

- **postgres**: основная база данных для хранения пользователей и задач.
- **redis**: брокер сообщений для Celery и временное хранилище для фоновых задач.
- **opensearch**: движок полнотекстового поиска по задачам.
- **gateway**: API Gateway на FastAPI, обрабатывает входящие запросы и проверяет JWT.
- **auth**: сервис аутентификации (регистрация, логин, выдача токенов).
- **domain**: основной бизнес-сервис (CRUD задач, валидация, публикация событий).
- **worker**: Celery-воркер для асинхронной индексации в OpenSearch.
- **sentry**: централизованная система сбора ошибок (self-hosted или cloud).

**Контрольная точка**:  
После запуска `docker compose up` эндпоинт `http://localhost:8000/health` возвращает:
  '''json status ok'''

### 7. Авторизация и безопасность


Система использует JWT (JSON Web Token) для аутентификации пользователей.

- **JWT**: токен содержит `user_id` и выдаётся после успешного логина.
- **Access Token TTL**: 15 минут — достаточно для сессии, но минимизирует риски при утечке.
- **Refresh-токены**: не реализованы в MVP (для упрощения архитектуры).
- **Хеширование паролей**: используется алгоритм `bcrypt`.
- **Проверка токена**: выполняется **в API Gateway** — все защищённые эндпоинты проходят валидацию перед маршрутизацией в сервисы (`auth`, `domain`). Это централизует безопасность и снижает дублирование логики.

### 8. Поиск (OpenSearch)

Поиск реализован с использованием **OpenSearch** — open-source форка Elasticsearch, оптимизированного для производительности и безопасности.

- **Индексация**: происходит асинхронно через Celery при создании или обновлении задачи.
- **Поля для поиска**: `title`, `description` (полнотекстовый поиск с поддержкой частичных совпадений).
- **Логирование**:
  - Все поисковые запросы логируются в структурированном формате (JSON),
  - В логах фиксируются: `user_id`, `search_query`, `timestamp`, `duration_ms`,
  - Ошибки индексации и поиска отправляются в Sentry.

Это обеспечивает прозрачность использования поиска и упрощает диагностику проблем.

### 10. Observability

Система обеспечивает полную наблюдаемость через следующие механизмы:

- **Структурированные логи**: все логи выводятся в формате JSON с полями `timestamp`, `level`, `message`, `service`, `request_id`. Это позволяет легко агрегировать и анализировать логи (например, через Loki или ELK).
- **request_id**: генерируется API Gateway для каждого входящего HTTP-запроса и добавляется в логи всех сервисов. Позволяет отследить путь одного запроса через всю систему.
- **correlation_id**: совпадает с `request_id` и передаётся между сервисами через заголовок `X-Correlation-ID`. Обеспечивает сквозную трассировку даже при асинхронных вызовах.
- **Sentry**: все необработанные исключения и критические ошибки автоматически отправляются в Sentry с контекстом (user_id, request_id, тело запроса). Используется как self-hosted, так и cloud-версия.

Это позволяет быстро диагностировать проблемы, отслеживать производительность и анализировать поведение пользователей.

##  11. MVP

- **Auth**: регистрация и вход по email/паролю с выдачей JWT-токена.
- **CRUD**: полный набор операций над задачами: создание, чтение, обновление, удаление.
- **PostgreSQL**: основная база данных для хранения пользователей и задач.
- **Docker Compose**: единый файл docker-compose.yml для запуска всей инфраструктуры.
- **1 фоновый сценарий**:асинхронная индексация новой/обновлённой задачи в OpenSearch через Celery + Redis.
- **Базовый поиск**: полнотекстовый поиск по полям title и description через OpenSearch.
- **Observer (инструмент)**: интеграция с Sentry для сбора и отслеживания ошибок.

### 12. План спринтов

Разработка разбита на 3 спринта, ориентированных на архитектурные вехи:

- **Спринт 1: Базовый каркас**  
  Реализация ядра системы:  
  - Auth Service (регистрация, JWT)  
  - Domain Service (CRUD задач)  
  - PostgreSQL как основная БД  
  - Docker Compose для запуска  
  - Эндпоинт `/health` → `{"status":"OK"}`

- **Спринт 2: События и поиск**  
  Добавление асинхронности и поиска:  
  - Интеграция Redis + Celery  
  - Публикация событий при изменении задач  
  - Фоновая индексация в OpenSearch  
  - Эндпоинт `/search`

- **Спринт 3: Улучшения**  
  Повышение надёжности и удобства:  
  - Интеграция Sentry (ошибки, контекст)  
  - Структурированные логи + request_id  
  - Пагинация и расширенная фильтрация  
  - Документация и финальное тестирование
